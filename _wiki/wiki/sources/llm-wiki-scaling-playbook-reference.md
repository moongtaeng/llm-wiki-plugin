# llm-wiki 스킬 스케일링 플레이북 레퍼런스

`references/scaling-playbook.md`는 위키 구조가 진화해야 하는 임계값과 그 마이그레이션 절차를 규정한다. 목표는 위키가 커져도 질의당 컨텍스트 비용이 대략 일정하게 유지되는 것 — 위키가 커졌다는 이유만으로 더 많은/더 큰 페이지를 읽게 만들면 안 된다.

## 병목의 4가지 구체적 실패와 구조적 해법

인덱스 파일이 읽기 비싸질 만큼 커짐 → 카테고리별 샤딩. 페이지가 무한정 커짐 → 크기 캡 강제 및 위반 시 분할. 인덱스 요약이 너무 모호해져 후보를 구분 못 함 → 요약을 조이고 검색 스크립트의 frontmatter 필터링 도입. 브루트포스 grep이 인덱스 우선 탐색을 대체함 → 인덱스를 실제로 유용하게 만들고 검색 스크립트를 명시적 폴백으로 사용.

## 5단계 임계값

- **~50페이지 이하**: 거의 구조가 필요 없다. 플랫 `wiki/` + `index.md` + `log.md`로 충분. 카테고리 서브디렉터리는 공짜이므로 처음부터 써도 된다.
- **~150페이지 또는 index.md 300줄 초과**: **인덱스 샤딩** — `wiki/indexes/` 생성, 카테고리별로 `indexes/sources.md` 등으로 분할, 최상위 `index.md`를 샤드 디렉터리로 재작성(50줄 미만이 되어야 함), 스키마에 샤딩 구조 문서화.
- **~300페이지**: **검색 스크립트를 상용 폴백으로 사용**. 직접 인덱스 탐색은 여전히 동작하지만 fuzzy 질의는 로컬 semantic+BM25 기본 랭킹의 이득을 받는다.
- **~500페이지**: **구조 린트 cadence를 주간/N회 인제스트마다로 전환**(수동 감독이 확장되지 않으므로). 검색 스크립트가 영속 파싱 캐시(`--cache`)를 원할 수 있다 — 콘텐츠 해시 기반이라 변경된 페이지만 재파싱되고 결과는 캐시 없는 실행과 항상 동일하다. 위키가 서로 교차 참조하지 않는 별개의 토픽 클러스터로 유기적으로 갈라졌다면 위키 자체를 분할하는 것도 고려한다.
- **~1,000+페이지**: LLM Wiki 패턴이 여전히 맞는 도구인지 재고할 시점. gist 저자는 ~100개 아티클/~40만 단어 규모에서도 잘 동작한다고 보고하지만, 질의가 압도적으로 관계형이거나(그래프 DB가 낫다) 린트 리포트가 높은 cadence에서도 감당 못 할 만큼 길거나 스키마가 수십 개 타입/수백 개 태그로 불어났다면 실제 데이터베이스로의 마이그레이션 신호다. 마크다운 위키(frontmatter + 위키링크)는 property graph로의 마이그레이션에 좋은 입력이 된다.

## 언제 샤딩하지 않을지

샤딩은 되돌리기 번거로우므로(un-shard는 가능하지만 성가심) 실제 임계값이 오기 전에 미리 하지 않는다. 80페이지짜리 위키에 샤딩된 인덱스는 플랫 인덱스보다 사용성이 나쁘다 — 볼륨이 정당화하지 못하는 탐색 단계를 추가하기 때문이다.

## 커스텀 페이지 타입 도입 시점

기본 4타입(source/entity/concept/synthesis)이 대부분을 커버한다. 사용자가 어떤 기본 타입에도 맞지 않는 명확한 카테고리를 가지고 있고 그것이 별도 서브디렉터리(쿼리 가능, 별도 린트 규칙, 별도 템플릿)로 이득을 볼 때만 타입을 추가한다(예: 팀의 `decision` 페이지, 연구소의 `experiment` 페이지). 일회성엔 타입 대신 태그를 쓴다 — 타입 추가는 인덱스, 린트 스크립트, 향후 모든 인제스트에 영향을 미치는 스키마 변경이다.

## "컨벤션을 넘어섰다"는 신호

같은 종류의 frontmatter 문제가 반복 재발, 어떤 기존 타입에도 안 맞는 페이지가 계속 생성됨, 태그 목록이 다루기 힘들어짐, 사용자가 특정 종류의 판단을 계속 오버라이드함 — 이런 신호는 더 많은 린트가 아니라 스키마 개정이 필요하다는 뜻이다.
